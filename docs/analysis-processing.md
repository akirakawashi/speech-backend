# Фоновый анализ в бэкенде

Реализовано 13.10.2026. Команда `speech-analyze` — самостоятельный CPU-процесс
того же проекта `speech-backend`. Она берёт только задания `analyze` из
существующей PostgreSQL-очереди. HTTP API быстро подтверждает приём ASR;
анализ запускается отдельно после сохранения расшифровки.

Оценка `evaluate` реализована в общем `speech-process`:
[локальная оценка и расписание](evaluation-processing.md).
Дополнительные команды причин/свободной классификации и удаление переходного
кода остаются следующими задачами. Новых миграций,
брокера и репозитория нет. Серверы этой работой не переключались.

## Запуск и зависимости

Из каталога бэкенда после `uv sync --locked`:

```bash
uv run --locked speech-analyze
uv run --locked speech-analyze --lanes daily,backfill --once
```

Эквивалентная точка входа —
`uv run --locked python -m src.presentation.cli.analysis_processor`.
По умолчанию процесс читает `daily,backfill` и последовательно исполняет
по одному анализу. `--once` восстанавливает просроченные задания этих полос,
обрабатывает не больше одного готового задания и выходит. При пустой очереди
это штатное завершение. В постоянном режиме проверка очереди идёт каждые
две секунды; сборщик просроченных заданий — каждые 60 секунд.

| Настройка | Назначение |
|---|---|
| `SPEECH_MS_DATABASE_URL` | Общая с API база речи, схема `sp_0016_evaluation_jobs` |
| `SPEECH_ANALYSIS_LLM_BASE_URL` | Корень Chat Completions API, обычно с `/v1` |
| `SPEECH_ANALYSIS_LLM_API_KEY` | Ключ модели, если сервис требует авторизацию |
| `SPEECH_ANALYSIS_LLM_MODEL` | Модель анализа, прежнее значение по умолчанию |
| `SPEECH_ANALYSIS_LLM_TIMEOUT_SECONDS` | HTTP-бюджет одного вызова, по умолчанию 120 секунд |
| `SPEECH_ANALYSIS_LLM_MAX_TOKENS` | Лимит ответа, по умолчанию 8192 |

Промпты и параметры готовятся локально через `LocalModelRequestPreparer`.
Процесс не обращается к API бэкенда за промптом и не требует служебного токена,
Whisper, MinIO, аудиофайлов, ffmpeg, CUDA или PyTorch. Ключ модели поступает
только в окружение исполнителя и заголовок запроса LLM; в задания он не входит.
Рабочие `.env` сохраняются; шаблон уже содержит перечисленные настройки.

CPU-образ собирается из цели `speech-analysis`:

```bash
docker build --target speech-analysis -t speech-backend-analysis:local .
```

Его команда по умолчанию — `speech-analyze`, пользователь — `10001:10001`.
Сборка устанавливает зависимости через UV и проверяет точку входа. Локальный
Compose пока запускает API и миграции; этот процесс запускается отдельно.
Инструкция с явной передачей настроек: [развёртывание](deployment.md#cpu-обработчик-анализа).

Роль PostgreSQL должна читать справочники и расшифровки, изменять звонки,
задания, роли реплик и оценки, а также иметь право на `LOCK TABLE ... SHARE`
для `speech_classifier_nodes` и `speech_call_reasons`. Сборка процесса сначала
проверяет ревизию схемы. Миграции он самостоятельно не применяет.

## Слои

| Место | Ответственность |
|---|---|
| `presentation/cli/analysis_processor.py` | Аргументы CLI → `AnalysisProcessorOptions` |
| `di/analysis_processor.py` | Настройки, LLM, пул базы, проверка схемы, сигналы и закрытие ресурсов |
| `application/analysis/execution.py` | Подготовка входа, вызов LLM и существующий `AnalysisInterpretationService` |
| `application/analysis/processing.py` | Снимок, обработка и атомарное подтверждение результата либо отказа |
| `application/ports/analysis_processing.py` | Хранение снимка и транзакция результатов |
| `domain/calls/analysis_processing.py` | Правило действующего захвата задания |
| `infrastructure/persistence/analysis_processing.py` | PostgreSQL, блокировки, сравнение входа и commit |
| `infrastructure/runtime/analysis_processor.py` | Совместимый режим общего runtime только для анализа |
| `infrastructure/runtime/job_processor.py` | Общий цикл очереди, heartbeat, восстановление и остановка |

Правила nonce/аренды и общие операции PostgreSQL выделены в
`domain/calls/job_processing.py` и `infrastructure/persistence/job_processing.py`.
Модули анализа сохраняют свои имена и делегируют общие операции; оценка использует
те же правила захвата и runtime без копирования цикла.

Сохранённый `AnalyzeHandler` бэкенда делегирует вычисление тому же
`AnalysisExecutionService`. Правила разбора не копируются. Его старые CLI
остаются переходными потребителями; совместный запуск прежнего общего
LLM-воркера и нового процесса для одной базы не является порядком переключения.

## Снимок и атомарность

1. Захват выдаёт идентификатор звонка/задания, владельца, номер попытки и новый
   nonce `_claim_token`. Проверяются вид `analyze`, статус `running` и живая аренда.
2. Короткая транзакция `REPEATABLE READ` читает транскрипт, реплики, роли,
   классификатор и справочник причин. Соединение освобождается до HTTP-вызова.
3. `AnalysisExecutionService` вызывает LLM и интерпретатор. Прежний предел
   неправильного формата — три ответа; сетевой отказ возвращается очереди.
4. Транзакция записи блокирует звонок, его задания, транскрипт и реплики.
   Справочники кратко блокируются в `SHARE NOWAIT`, включая защиту от вставок.
   Занятая блокировка или другой активный этап дают отсрочку.
5. Проверяются nonce, владелец, попытка, срок по времени базы и хеш текущего
   входа. Хеш включает идентичность/дату транскрипта, текст, роли и справочники.
   Порядок строк справочников на сравнение не влияет.
6. Результат, роли, снятие прежней оценки при изменении ролей, состояния звонка
   и `done` задания фиксируются вместе. Последний UPDATE ещё раз проверяет
   живую аренду; его отказ откатывает все записи. Успех сообщается после commit.

При изменении входа анализ откладывается на 60 секунд с возвратом попытки.
Проектные значения сегмента/продукта сохраняются; измеренные роли стереозаписи
не заменяются ответом LLM. После обычного успешного анализа новое `evaluate`
автоматически не создаётся: оценка остаётся независимым сценарием.

## Отказы, восстановление и остановка

Сетевые ошибки используют прежний backoff очереди и её бюджет попыток.
Терминальный отказ атомарно ставит задание в `dead`, анализ — в `failed`,
звонок — в `done`; расшифровка остаётся доступной. Ошибка самой транзакции
не превращается в подтверждённый результат: задание восстанавливается по аренде.

Heartbeat продлевает только тот же живой nonce. При потере аренды или трёх
последовательных ошибках heartbeat задача анализа отменяется; старый процесс
не может записать результат нового захвата. HTTP-вызов мог уже дойти до модели,
поэтому повтор после аварии допускает повторный инференс, но не частичный commit.

CPU-сборщик возвращает только `analyze` выбранных полос. Если последняя попытка
просрочена, отказ звонка переносится отдельно под блокировками. Обрыв между
`dead` и этой проекцией исправляется следующим циклом. Повторная постановка
или новый этап получения/распознавания запрещают позднюю запись отказа.
Сборщик основного аудиоворкера ограничен его этапами и полосами.

SIGTERM/SIGINT запрещают новые захваты и позволяют завершить текущий анализ.
Принудительная остановка оставляет незавершённое задание для восстановления.
При будущей настройке Kubernetes срок штатной остановки должен учитывать до
трёх вызовов модели и запись результата. Пул закрывается в `finally`.

В журнал попадают UUID, исход и класс/тип ошибки; исходный текст, тело ответа
и ключи не выводятся. Проверки находятся в `test_analysis_processor.py` и
`test_analysis_processor_db.py`: настоящая PostgreSQL, подставной HTTP модели,
включая цепочку приём ASR → отдельный CPU-процесс → результат.
