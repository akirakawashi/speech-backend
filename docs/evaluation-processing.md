# Фоновая оценка и единый CPU-процесс

Реализовано 13.10.2026. `speech-process` — процесс проекта `speech-backend`,
который последовательно выполняет `analyze` и `evaluate` из общей PostgreSQL.
Он готовит промпты локально, вызывает отдельные HTTP-сервисы моделей и
сохраняет результаты. Аудиоворкер исполняет получение/распознавание/доставку ASR.

## Запуск

После `uv sync --locked` из каталога бэкенда:

```bash
uv run --locked speech-process
uv run --locked speech-process --stages evaluate
uv run --locked speech-process --stages evaluate --no-schedule --once
```

Эквивалентная точка входа — `src.presentation.cli.speech_processor`.
По умолчанию выбраны `analyze,evaluate` и полосы `daily,backfill`. Один процесс
держит не больше одного модельного задания. Сохранённый `speech-analyze`
исполняет только анализ через тот же цикл и правила; для обычного запуска
анализа и оценки используем один `speech-process` вместо двух исполнителей.

`--once` проверяет схему, восстанавливает свои просроченные задания,
при включённом расписании ставит порцию оценки, обрабатывает не больше одного
доступного задания и выходит. `--no-schedule` оставляет только исполнение
уже поставленных заданий. Для отдельной полосы истории этот режим позволяет
не ставить новую глобальную порцию оценки.

CPU-образ — цель `speech-processing`, команда образа — `speech-process`:

```bash
docker build --target speech-processing -t speech-backend-processing:local .
```

Образ запускается пользователем `10001:10001`; ffmpeg, CUDA и PyTorch ему
не нужны. Настройки Whisper, MinIO и служебный токен для этого процесса не нужны.
Локальный Compose по-прежнему содержит API и миграции; CPU-процесс запускается
отдельно. При размещении в Kubernetes начальный режим — одна реплика.
Миграции при старте не применяются; нужна `sp_0016_evaluation_jobs`.

| Настройка | Кто использует |
|---|---|
| `SPEECH_MS_DATABASE_URL` | Общая база речи, короткие чтения и транзакции записи |
| `SPEECH_ANALYSIS_LLM_*` | Только при выбранном `analyze` |
| `SPEECH_QUALITY_LLM_BASE_URL`, `SPEECH_QUALITY_LLM_API_KEY` | Адрес и ключ модели оценки при выбранном `evaluate` |
| `SPEECH_QUALITY_LLM_MODEL` | Имя модели оценки, по умолчанию прежнее `qwen3.8-27b-fast` |
| `SPEECH_QUALITY_LLM_TIMEOUT_SECONDS` | HTTP-бюджет одного запроса оценки, по умолчанию 180 секунд |
| `SPEECH_QUALITY_LLM_MAX_TOKENS` | Лимит ответа оценки, по умолчанию 4096 |
| `SPEECH_QUALITY_INTERVAL_SECONDS` | Интервал независимой постановки, по умолчанию 900 секунд |
| `SPEECH_QUALITY_BATCH_LIMIT` | Размер порции постановки, по умолчанию 100 |
| `SPEECH_DISPLAY_TIMEZONE` | Привязка границ расписания, по умолчанию `Europe/Moscow` |

Запуск только оценки не требует модели анализа, и наоборот. Ключи моделей
остаются в окружении бэкенда и HTTP-заголовках, в задания не передаются.
Рабочие `.env` не перезаписываются; поддерживаемые поля уже есть в шаблоне.

## Независимая постановка

`EvaluationProcessorSchedule` вызывает локальный `WorkerMaintenanceService.enqueue`.
Служебный токен и HTTP к API собственного проекта здесь не используются.
Прежний `enqueue_authorized` сохранён для переходных клиентов и проверяет доступ.

На старте выполняется одна порция. Затем сохраняются прежние границы интервала
и догон после простоя. Планировщик работает отдельной задачей event loop и
продолжает постановку во время ожидания LLM. Модельные задания исполняются
последовательно. Срок следующей постановки вычисляет domain; ошибка базы не
переносит успешный момент запуска вперёд.

Выбор и запись остаются в `PostgresQualityQueueRepository`: только готовые
звонки Телфина, текущая редакция скрипта, `skip_failed`, ограниченная порция,
отсутствие активного `evaluate` и дедупликация под блокировкой звонков.
Приоритет оценки не ниже 30 и наследует полосу/приоритет анализа. Оценка не
является обязательным продолжением `analyze`: приём ASR не ждёт ни одну модель,
а завершение анализа само по себе не создаёт оценку.

## Сценарий и слои

| Место | Ответственность |
|---|---|
| `presentation/cli/speech_processor.py` | Аргументы → `SpeechProcessorOptions`; отвергает `ingest`/`transcribe` |
| `di/speech_processor.py` | Только выбранные модели, база, проверка схемы, сигналы и закрытие пула |
| `application/quality/computation.py` | Общий локальный сценарий без записи: роли, оценка, проверка и нормализованный исход |
| `application/quality/processing.py` | Допуск, снимок, повторы и атомарное подтверждение `evaluate` |
| `application/quality/processor_schedule.py` | Независимая постановка по существующим правилам |
| `domain/quality/processing.py` | Допуск источника и готовности версии входа |
| `domain/calls/job_processing.py` | Вид, nonce, владелец, попытка, живая аренда и конфликт этапов |
| `infrastructure/persistence/evaluation_processing.py` | Чтение/блокировки и запись оценки вместе с заданием |
| `infrastructure/persistence/job_processing.py` | Общие операции nonce, backoff, отсрочки и UoW |
| `infrastructure/runtime/job_processor.py` | Общий цикл, heartbeat, восстановление, планировщик и остановка |

`compute_quality` использует существующие `prepare_roles`, `evaluate`, скрипт
и разбор ответа. Переходный HTTP-контракт шагов вызывает тот же сценарий с
записанными ответами. Второй реализации правил нет. Сохранены атрибуция моно,
доверенные роли стерео, три повтора неправильного формата, отдельная проверка
черновика, ссылки на реплики, расчёт балла и предел 1024 модельных запросов.

## Актуальность и commit

В начале короткая `REPEATABLE READ` проверяет живой nonce `evaluate` и читает
источник/готовность звонка, UUID/дату транскрипта, метод ролей, реплики и
серверный момент чтения. Соединение освобождается до первого LLM-запроса.
NCC и отсутствие транскрипта не вызывают модель. Ожидающий предшествующий этап
откладывает оценку без расхода попытки.

При записи блокируются звонок, его задания, транскрипт и реплики. Проверяются
nonce, владелец, попытка, срок по времени базы и полное равенство DTO входа.
Новый UUID транскрипта отвергает старый результат даже при одинаковых тексте
и дате. Изменение текста, ролей, таймкодов, метода или источника также даёт
отсрочку на 60 секунд с возвратом попытки. Занятые блокировки используют NOWAIT.

Роли, снятие прежних оценок при изменении ролей, итог оценки либо её отказ
и `done` задания фиксируются одной транзакцией. Последний UPDATE ещё раз
проверяет живую аренду; его отказ откатывает все записи. Более новый успешный
результат не заменяется поздним ответом. Статус готового звонка и его
`completed_at` оценка не переписывает.

## Ошибки и остановка

Повторяемый сетевой отказ до последней попытки возвращает задание с прежним
backoff. На последней попытке сохраняются `model_error` и завершённое задание.
Непригодный формат даёт `invalid_evaluation`, неопределённые роли —
`roles_undetermined`. Это отсутствие оценки с NULL баллом; нулевой результат
за провал модели не выставляется. Определённые моно-роли сохраняются вместе
с поздним отказом. Действующая успешная оценка по тому же входу сохраняется
при неудавшейся переоценке.

Потеря heartbeat/nonce отменяет устаревшее вычисление. Авария до commit оставляет
задание для возврата по аренде; новое выполнение получает новый nonce.
Сборщик ограничен выбранными видами и полосами. Исчерпание аренды на последней
попытке даёт `dead` в очереди и сохраняет готовность звонка; синтетическую
оценку по неизвестному входу сборщик не создаёт.

SIGTERM/SIGINT запрещают новые захваты и ждут текущее модельное задание.
Из-за нескольких запросов оценки фиксированного малого срока остановки
недостаточно: будущий `terminationGracePeriodSeconds` выбирается по нагрузке
и HTTP-бюджету. Принудительное завершение допускает повторный инференс,
но не частичную запись оценки. Пул базы закрывается в `finally`.

Проверки: `test_evaluation_processor.py`, `test_evaluation_processor_db.py`,
существующие проверки качества и анализа. Есть настоящая PostgreSQL с
подставным HTTP модели и путь ASR → анализ → независимая оценка одним процессом.
Качество настоящих моделей и запуск на сервере этими тестами не измеряются.
