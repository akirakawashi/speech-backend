# Прямое выполнение запросов к LLM

Главное правило 13.10.2026: все LLM-вызовы, анализ, оценка и сохранение итогов
переходят в бэкенд. Воркер распознаёт и доставляет расшифровку.
[Владельцы операций](processing-ownership.md).
Этот документ описывает текущие переходные контракты и настройки от 12.10.2026;
они ещё работают, но исполнение готовых LLM-запросов воркером больше не является целью.
После подключения доставки ASR 13.10.2026 основные реестр и CLI воркера
вообще не берут analyze/evaluate. Описанные здесь вызовы доступны только
сохранённым отдельным переходным потребителям. CPU-команда `speech-analyze`
уже готовит запрос локально, вызывает модель и сохраняет итог:
[фоновый анализ](analysis-processing.md). `evaluate` также исполняется локально: [единый процесс](evaluation-processing.md).
[Актуальная доставка](../../speech-worker/docs/transcription-delivery.md).

Решение владельца 12.10.2026: новые проекты вызывают LLM напрямую.
Зависимость от Dify, его ключи приложений и YAML-сценарии удалены.
Внешний экземпляр Dify и исходный `whisper-backend` не изменяются.

## Владение решениями

Бэкенд определяет, нужен ли вызов LLM, выбирает сценарий, промпт и модель,
сам выполняет HTTP-вызов и сохраняет итог. Воркер получает запись, готовит
аудио, вызывает Whisper и доставляет результат. Новые LLM-сценарии
в воркер не добавляются; существующие остаются до переноса.

Переход пока завершён для подготовки запросов анализа, причин обращения,
свободной классификации и сравнения с выбором оператора. Существующая очередь
PostgreSQL, постановка следующих этапов и прикладной разбор ответов сохранены.
Часть прежних правил конвейера всё ещё есть в выделенном воркере и в старых
CLI бэкенда. Их перенос в бэкенд — следующий этап разделения; это изменение
не означает, что воркер уже стал полностью техническим исполнителем.

13.10.2026 в бэкенде проверка и интерпретация ответа анализа выделены
в самостоятельный application-сервис с DTO и правилами domain. Существующий
обработчик бэкенда и новый CPU-процесс используют этот сервис;
новый HTTP-вызов разбора LLM-ответа из воркера не планируется.
[Границы сервиса и сохраняемое поведение](analysis-interpretation.md).

## Промпты и слои

Четыре версионированных ресурса находятся в
`src/infrastructure/data/prompts/`:

| Сценарий | Ресурс | Модель по умолчанию |
|---|---|---|
| `analysis` | `analysis.json` | `qwen3.8-27b-fast` |
| `reason` | `reason.json` | `qwen3.8-27b-fast` |
| `free_classification` | `free_classification.json` | `qwen3.8-27b` |
| `operator_compare` | `operator_compare.json` | `qwen3.8-27b` |

Содержание перенесено из прежних сценариев без изменения инструкций модели.
Изменился синтаксис переменных: `{{segments}}` вместо ссылки на узел Dify.
Версия каждого промпта — `1.0`. Ресурсы включаются в пакет бэкенда;
каталог инфраструктуры читает их через `importlib.resources`.

`ModelRequestService` в application проверяет обязательные поля и ограничения,
рендерит сообщения и выбирает модель. JSON сериализуется с сохранением кириллицы,
bool — как 0 или 1; текст звонка подставляется один раз и не исполняется как шаблон.
Необязательный справочник причин в анализе может отсутствовать.
Сценарий сравнения моделей выбирает `candidate`; его модель должна быть настроена
и отличаться от production. Температура — 0, лимит ответа по умолчанию — 8192.

Оценка продаж уже вызывала модель напрямую; её отдельные
`SPEECH_QUALITY_LLM_*` и действующие правила Телфина сохранены.

## Служебный HTTP-контракт 1.0

`POST /internal/v1/model-requests` получает `ModelPreparationRequest`:

```json
{
  "contract_version": "1.0",
  "scenario": "analysis",
  "profile": "production",
  "inputs": {
    "call_id": "c-1",
    "needs_roles": 1,
    "classifier": {},
    "segments": [{"seq": 1, "speaker": "unknown", "text": "Здравствуйте"}]
  }
}
```

Ответ `PreparedModelRequest` содержит `contract_version`, `scenario`,
`profile`, `prompt_version`, `model`, `messages`, `temperature` и `max_tokens`.
URL модели и ключ доступа в DTO отсутствуют: они принадлежат окружению исполнителя.
Маршрут не использует БД и скрыт из OpenAPI браузера.

Доступ — `Authorization: Bearer <SPEECH_WORKER_API_TOKEN>`.
Токен должен совпадать в двух проектах; браузерный режим `open` его не отменяет.
Пустая настройка бэкенда закрывает маршрут с 503, неверный токен даёт 401,
некорректный DTO или вход сценария — 422 без исходных значений.
Между серверами используем защищённый внутренний канал или HTTPS.

Воркер проверяет версию, профиль, сценарий и форму ответа, затем отправляет
готовые сообщения в `<SPEECH_ANALYSIS_LLM_BASE_URL>/chat/completions`.
Ответ модели передаётся существующему разбору под ключом `answer`.
Сетевые ошибки, 408, 429 и 5xx допускают повтор; остальные 4xx,
неизвестный контракт, отказ модели и обрыв ответа по лимиту — окончательный
отказ текущей попытки. Тела ответов и секреты в причины ошибок не добавляются.

## Настройки и переход

На бэкенде задаём:

- `SPEECH_WORKER_API_TOKEN` — служебный токен.
- `SPEECH_ANALYSIS_LLM_MODEL` и `SPEECH_ANALYSIS_LLM_FREE_MODEL` — модели.
- `SPEECH_ANALYSIS_LLM_CANDIDATE_MODEL` — необязательная модель для сравнения.
- `SPEECH_ANALYSIS_LLM_MAX_TOKENS` — лимит ответа.

В окружении воркера нужны:

- `SPEECH_BACKEND_BASE_URL` — доступный с GPU-сервера адрес API без `/internal/v1`.
- `SPEECH_WORKER_API_TOKEN` — тот же токен.
- `SPEECH_BACKEND_TIMEOUT_SECONDS` — таймаут подготовки, по умолчанию 30 секунд.
- `SPEECH_ANALYSIS_LLM_BASE_URL` — адрес модели с `/v1`.
- `SPEECH_ANALYSIS_LLM_API_KEY` — ключ модели; для локального сервера может быть пустым.
- `SPEECH_ANALYSIS_LLM_TIMEOUT_SECONDS` — таймаут инференса, по умолчанию 120 секунд.

Старые `SPEECH_DIFY_*` больше не используются. Значения в рабочих `.env`
автоматически не меняются. Сначала настраиваем и выкладываем API со служебным
маршрутом, затем обновляем настройки и запускаем воркер. Для новой очереди оценки требуется миграция `sp_0016_evaluation_jobs`.
Список моделей проверяем на настоящем сервере перед переключением.

Сохранённые CLI бэкенда готовят запрос через тот же application-сервис локально,
без HTTP-вызова самому себе. Для их запуска дополнительно нужны адрес
и ключ LLM в окружении бэкенда. В контейнере API ключ инференса не передаётся.

`SPEECH_BACKEND=speech-backend ./local-dev/themes.sh` использует локальную LLM
напрямую и обнаруживает её model ID. Заглушка Dify остаётся только для прежних
бэкендов; новые проекты не читают их файлы.

## Проверки

Тесты покрывают содержание промптов, контракт входа и выхода, выбор моделей,
служебную авторизацию, отдельные ключи, HTTP-ошибки и совместимость разбора.
Полные наборы с PostgreSQL проверяют сохранённый конвейер.
Проверки с подставной моделью подтверждают транспорт и сериализацию;
качество и скорость реальной GPU-модели требуют прогона на сервере.

## Оценка в общей очереди

Бэкенд выбирает звонки Телфина, подготавливает роли, оценку и проверку,
разбирает ответы модели. `SPEECH_QUALITY_LLM_MODEL` и лимит ответа задаём
в бэкенде; URL, ключ и таймаут сервера модели — в воркере.
Оценка выполняется последовательно с остальными заданиями и не меняет
статус готовой расшифровки. Частные маршруты используют тот же ключ доступа.
[Служебный контракт, повторы и переключение](worker-runtime.md).
