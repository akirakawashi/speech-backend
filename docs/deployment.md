# Локальный запуск бэкенда в Docker

`docker-compose.yml` принадлежит проекту `speech-backend`. Он запускает API
и отдельную команду миграций. Обработка записей выполняется в самостоятельном
`speech-worker`; PostgreSQL и MinIO подключаются как внешние сервисы.
Целевое размещение API — Kubernetes на CPU, Compose нужен для локального запуска.

## Сервисы и образы

| Сервис | Назначение | Запуск | Цель Dockerfile | Локальный образ |
|---|---|---|---|---|
| `speech-ms` | HTTP API | Обычный `docker compose up` | `speech-ms` | `speech-backend:local` |
| `migrate-speech` | Применение миграций базы речи | Явный `docker compose run` с профилем `operations` | `migrations` | `speech-backend-migrations:local` |

Переменные `SPEECH_MS_IMAGE` и `SPEECH_MIGRATIONS_IMAGE` позволяют указать
заранее собранные образы. API доступен хосту через `127.0.0.1:18096`;
порт хоста меняется переменной `AICISTENT_SPEECH_MS_DOCKER_PORT`.
Порт контейнера — `8096`. Фиксированного `container_name` нет:
имя контейнера назначает Compose.

Миграции запускаются отдельно перед API. У API нет зависимости `depends_on`
на команду миграций, поэтому обычный запуск или перезапуск API не меняет схему.
Ожидание готовности обращается к `/ready`: проверяются подключение PostgreSQL
и ревизия `sp_0016_evaluation_jobs`.

## Настройки базы и сети

Для Compose заполняются два отдельных адреса в `.env`:

- `AICISTENT_DOCKER_SPEECH_MS_DATABASE_URL` — роль `speech_ms_runtime` для API.
- `AICISTENT_DOCKER_SPEECH_MS_MIGRATE_DATABASE_URL` — роль `speech_ms_migrate`
  для миграций.

Оба адреса обязательны и передаются своему процессу под именем
`SPEECH_MS_DATABASE_URL`. Автоматической подстановки учётной записи API
для миграций нет. При запуске через UV вне Docker приложение и Alembic читают
`SPEECH_MS_DATABASE_URL` напрямую. Имена двух переменных Compose и переменной
порта сохранены для совместимости с заполненными окружениями.

API и миграции используют одну внешнюю сеть `SPEECH_DOCKER_NETWORK`.
В шаблоне и по умолчанию указана `speech-data`. Сеть должна существовать
до запуска; Compose её не создаёт. Для PostgreSQL в Docker укажите его сеть,
чтобы имя хоста из адреса базы разрешалось внутри контейнера.
Если PostgreSQL находится на отдельном сервере, можно создать сеть для бэкенда
командой `docker network create speech-data` и установить
`SPEECH_DOCKER_NETWORK=speech-data`.

API дополнительно подключён к стандартной сети `default`, которую создаёт
Compose. Через неё он обращается к MinIO и Keycloak, даже если сеть
PostgreSQL настроена как `internal`. Миграции используют только сеть базы.

## Хранилище и окружение контейнеров

`SPEECH_STORAGE_BASE_URL` содержит адрес MinIO на отдельной машине,
доступный из контейнера API. В Compose нет локального MinIO и тома с записями.
API читает аудио из указанного бакета для воспроизведения; при пустом адресе
хранилища эта функция недоступна.

Compose использует `.env` для подстановки переменных. В контейнер поступают
только поля из `environment`: настройки API, авторизации, cookies, CORS
и чтения записей, служебный токен воркера и параметры выбора модели.
API готовит запросы по [контракту LLM](model-execution.md); ключ инференса,
настройки Whisper и источников звонков ему не передаются.
Миграции получают только адрес своей базы.
Файл `.env` не копируется в образ; шаблон находится в
[.env.example](../.env.example).

Оба процесса используют пользователя образа `10001:10001` и файловую систему
только для чтения; временные файлы находятся в `/tmp` на tmpfs.
Для API tmpfs ограничен одним гигабайтом: там создаются временные файлы
отчётов Excel. Ограничение сохраняется при изменениях Compose.

## Порядок запуска

Заполните `.env` по шаблону, проверьте адреса PostgreSQL и MinIO и задайте сеть
`SPEECH_DOCKER_NETWORK`. Затем:

```bash
docker compose --profile operations config --quiet
docker compose --profile operations build
docker compose --profile operations run --rm migrate-speech
docker compose up -d --wait
```

Для заранее собранных образов задайте обе переменные образов, пропустите
шаг `build`. Миграции запускайте той же командой `run`, API — командой
`docker compose up -d --wait --no-build`.

Миграциями общей схемы владеет бэкенд; отдельный воркер требует готовую ревизию.
Условия применения миграции, удаляющей обезличивание, описаны в
[контексте проекта](project-context.md#обезличивание-и-оценка).
Сохранённые служебные CLI и совместимая цель `speech-worker` в Dockerfile
пока остаются в исходниках бэкенда, но не запускаются его Compose.
