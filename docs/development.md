# Разработка и проверки

## Стандарт кода

Используем Python 3.12, Pydantic 2 для моделей и схем, Pydantic Settings для
конфигурации. Типы входа и выхода функций должны быть явными. Новый код должен
проходить строгий mypy; `Any` не заменяет описание известной структуры данных.

Имена описывают действие и предмет задачи. Функция отвечает за понятную
операцию, а зависимости получает явно. Асинхронный клиент используется через
асинхронный контракт; блокирующий ввод-вывод не выполняется прямо в event loop.
Не вводим новую библиотеку или абстракцию, если задача решается существующими.

У новых и изменённых функций, методов и классов пишем докстринги на русском.
Для функции объясняем:

- что она делает и зачем вызывается;
- что принимает, включая единицы измерения и ограничения, если они значимы;
- что возвращает, включая смысл `None`;
- какие значимые ошибки возможны;
- какие побочные эффекты возникают: запись, сетевой вызов, изменение состояния.

Используем разделы `Args`, `Returns` и при необходимости `Raises` и
`Side Effects`. У класса объясняем ответственность и ограничения, у модели —
смысл данных. Докстринг не пересказывает построчно реализацию.

Например, описание доменной функции расчёта балла:

```python
"""Рассчитать долю выполненных этапов скрипта.

Args:
    stages: Проверенные результаты этапов со значениями 0 или 1.

Returns:
    Доля выполненных этапов от 0 до 1.

Raises:
    ValueError: Если список этапов пуст.
"""
```

Это пример оформления, а не изменение существующего правила расчёта.

## Окружение

Все команды ниже выполняются из `speech-backend`. Используем только её
собственное окружение `.venv`. При установке явно выбираем интерпретатор:

```bash
uv pip install --python .venv/bin/python -e '.[all,dev]'
```

Так установка не зависит от того, какое окружение активно в терминале.
Проверки и версии инструментов задаются в [pyproject.toml](../pyproject.toml).

## Проверки

После изменения Python-кода запускаем:

```bash
.venv/bin/python -m ruff check .
.venv/bin/python -m ruff format --check .
.venv/bin/python -m mypy .
.venv/bin/python -m pytest -q
```

Вся Python-структура приведена к формату Ruff; проверка форматирования охватывает проект.

Ruff проверяет правила `E`, `F`, `I`, `UP`, `B`; длина строки — 100.
Импорты с псевдонимами группируем через `combine-as-imports`, чтобы реэкспорт
DTO и правил не превращался в повторяющиеся блоки одного модуля.
Mypy работает в строгом режиме с плагином Pydantic. Существующие послабления
для `tests.*` не являются разрешением ослаблять проверки рабочего кода.

Перед полным pytest задаём `SPEECH_POSTGRES_TEST_URL` с адресом отдельной базы
`speech_whisper_test` и применёнными миграциями `alembic` до `head`.
В этой папке удаление обезличивания представлено миграцией `sp_0015`.
Тесты с базой очищают таблицы `speech_*`, поэтому рабочая база для них не подходит.

Если Postgres недоступен, pytest пропускает соответствующие наборы. Такой
прогон не подтверждает поведение репозиториев и транзакций: в результате работы
указываем пропуски. На стенде и в CI используется `SPEECH_REQUIRE_LIVE_PROOFS=1`,
при котором пропуск этих наборов делает прогон неуспешным.

Не исправляем несвязанные старые ошибки молча. Если проверка падает, определяем,
связана ли ошибка с изменением, устраняем ошибки своей правки и сообщаем об
оставшихся ограничениях. Не добавляем `noqa`, `type: ignore` или исключения
проверок, чтобы скрыть проблему. Узкое исключение допустимо только при
подтверждённом ограничении внешней библиотеки, с объяснением рядом с кодом.

Для правок только Markdown проверяем локальные ссылки, команды и согласованность
документов. Ruff, mypy и pytest не проверяют содержание Markdown, поэтому такие
правки сами по себе не требуют повторного прогона Python-кода.

## Что проверяют тесты

- Домен: бизнес-правила, границы допустимых значений и результаты без внешних
  сервисов.
- Application: поведение сценария и ошибки через подставные реализации портов.
- Infrastructure: соответствие контракту порта, преобразование данных и реальные
  операции на тестовой базе, когда поведение зависит от PostgreSQL.
- Presentation: HTTP-контракт, преобразование ввода и результата, права и ошибки.
- DI: корректная сборка и время жизни ресурсов, если изменение затрагивает их.
- Архитектура: `tests/test_architecture.py` запрещает перескакивание слоёв,
  библиотеки ввода-вывода в domain/application и импорт DI в HTTP-роутерах.

При запуске в ограниченной среде контейнерная база и операции через фоновые
потоки могут быть недоступны. Такой запуск не заменяет полный прогон:
интеграционные проверки выполняем в среде с доступом к отдельной тестовой базе.

Тест должен подтверждать поведение или существенный контракт. Не пишем тесты,
которые просто повторяют устройство функции. При переносе сценария используем
существующие проверки и добавляем недостающие проверки существенного поведения.

При изменении внешнего API проверяем версию контракта, снимки в
`tests/contracts/` и `openapi.speech.json`. Правила работы со снимками описаны
в [README проекта](../README.md#снимки-контракта). Архитектурный перенос сам по
себе не требует изменения API.

Проверка контрактов сравнивает типы, обязательные поля, значения умолчания и
ограничения JSON Schema. `description` самой схемы — документация, поэтому
изменение докстринга не требует новой версии API. Поле данных с именем
`description` и содержимое значений `default` остаются частью сравнения;
старые снимки не переписываются при рефакторинге.

Новые инструменты проверок добавляем при появлении задачи, с командой запуска и
пояснением, что они проверяют. До этого не включаем несуществующие проверки в
обязательный список.
