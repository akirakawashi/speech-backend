# Атомарное хранение анализа и причины

Реализовано 14.10.2026. Бэкенд сохраняет актуальный разбор в
`speech_call_analyses`, а использованные справочники — в
`speech_analysis_references`. В той же транзакции обновляет прежние поля
`speech_calls`: существующие API, поиск, дашборд и отчёты продолжают читать их.
Одна строка на звонок; архива успешных результатов для сравнения нет.

Новой миграции не потребовалось: используется уже добавленная
`sp_0017_analysis_storage`. Рабочие БД, `.env`, зависимости и сервер этим шагом
не менялись. Массовый перенос старых данных и переключение чтения предстоят.

## Полный анализ

1. Бэкенд читает согласованный `AnalysisSnapshot` и освобождает соединение.
2. HTTP-клиент вызывает LLM, интерпретатор проверяет ответ. Получается
   `AnalysisComputation` с результатом и фактами пригодного запроса.
3. Транзакция блокирует звонок, задания, текст, реплики и справочники.
   Проверяет живой nonce/владельца/попытку и совпадение исходного снимка.
4. Application собирает `SaveAnalysis` и происхождение запроса: факты
   клиента, идентичность текста, исходный отпечаток, захват и версию правил.
5. Единое хранилище сохраняет снимок и актуальный анализ. Прежний SQL
   обновляет проекцию звонка и роли, снимает зависимые оценки.
6. Последняя проверка lease завершает задание. Успех сообщается после commit.

Ошибка последней проверки или commit откатывает обе проекции, новый снимок,
роли и снятие оценок. Просроченный ответ или изменённый ввод ничего не публикует.
Сетевые ошибки и лимиты формата сохраняют прежние классы и бюджет повторов.

Повторный успешный анализ заменяет весь модельный набор. UUID существующей
строки сохраняется, `revision` увеличивается. Причина из прежнего результата
удаляется, если её нет в новом полном анализе. Удаление/создание результата
после replay получает новый UUID; одна лишь ревизия не доказывает идентичность.

Таблица хранит предложенные LLM сегмент/продукт независимо от эффективных
измерений звонка. Проектные значения сохраняют прежний приоритет в
`speech_calls`. Текст причины без кода допустим в полном анализе.
Такая причина переиспользует происхождение и снимок полного анализа.

## Собственные роли и отпечатки

Исходный `analysis-snapshot/1` проверяется **до** применения собственных ролей.
Отдельный `transcript-state/1` содержит UUID/дату транскрипта, метод ролей и
упорядоченные `seq`/`speaker`/`text_raw` после их применения. Последнее
назначение одному seq побеждает, отсутствующие seq не создают реплик.
Он сохраняется в `committed_transcript_fingerprint` и не заменяет исходный хеш.

Последующая смена ролей оценкой не запускает скрытую переобработку анализа;
происхождение продолжает описывать состоявшийся запрос. Смена справочника
после commit также не снимает накопленные результаты автоматически.

## Отдельное дополнение причины

`speech-fill-reasons` сохраняет аргументы, отбор и отдельный запрос причины.
До LLM читает `ReasonSnapshot` в `REPEATABLE READ`: идентичность текста,
реплики/роли, включённые причины, ожидаемые UUID/revision анализа и прежнюю
проекцию полного анализа. Соединение закрывается до HTTP.

`ReasonComputation` сохраняет факты последнего ответа, версию
`reason-interpretation/1` и номер вызова, включая сетевые попытки.
Существующее сравнение получает только `ReasonAnswer` через прежний
`ask_reason` и ничего не записывает.

Сохранение блокирует звонок, транскрипт, реплики и справочник причин.
Сверяет `reason-snapshot/1`, UUID/revision, отсутствие заполненного кода.
При отсутствии новой строки дополнительно сверяет прежние модельные поля.
Занятые данные, заменённый текст, изменённый справочник, новый анализ либо
заполненная другим процессом причина дают `False` без частичной записи.

Отпечаток `reason-snapshot/1` — канонический JSON с ключами `transcript`
(`TranscriptState`, включая метод ролей и упорядоченные реплики) и `reasons`
(отправленные причины по коду). Ожидаемая запись и прежние поля в него не
входят и сравниваются отдельно. Канонизация — отсортированные ключи,
компактный JSON с `ensure_ascii=False`, UTF-8 и SHA-256.

Успех меняет причину, её происхождение/снимок, ревизию и время. Полная
классификация, резюме и их происхождение сохраняются. При отсутствии полного
анализа создаётся частичная строка; статус полного анализа не становится done.
Поздний полный анализ заменяет такой частичный набор по общему правилу.

Если новая строка отсутствует, а прежние колонки содержат полный анализ,
причина сначала сохраняет его проекцию в той же новой строке с
`legacy_observed`/`legacy_import`. Длинное старое резюме не обрезается.
Старая модель, время, исходное дерево и путь остаются неизвестными;
проектный сегмент/продукт не выдаётся за предложение LLM. Это совместимость
для затронутого звонка, не массовый перенос прежних результатов.

`FillReport.filled` учитывает только подтверждённые сохранения. Новый счётчик
`skipped` отличает изменившийся/уже заполненный вход от отказа LLM и ответа
без подходящего кода. При следующем запуске незаполненные звонки вновь
доступны для обычного отбора; отдельная фоновая очередь причин не добавлена.

## Снятие и срок жизни

Повтор `analyze`, `ingest` или `transcribe` удаляет текущий анализ в одной
транзакции с очисткой прежних полей и постановкой задания. Повтор `evaluate`
сохраняет анализ. Новый ASR явно снимает текущий результат перед заменой
текста; каскад FK остаётся дополнительной защитой. Повтор уже подтверждённой
доставки использует квитанцию и не снимает анализ нового текста.

Происхождение хранит сведения о задании как данные без FK. Очистка завершённых
заданий не удаляет актуальный анализ. Снимки справочников переиспользуются
через `(schema_version, fingerprint)` и никогда не обновляются при конфликте.
Использованные снимки защищены FK. Автоматическая очистка оставшихся без ссылок
снимков пока не вводилась; срок хранения будет определён общей политикой.
