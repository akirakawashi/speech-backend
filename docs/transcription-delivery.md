# Приём результата распознавания: служебный контракт 1.0

Реализована сторона бэкенда 13.10.2026. Маршрут принимает успешное
распознавание, проверяет выданное задание, сохраняет результат и ставит анализ.
Доставка из воркера подключена 13.10.2026. Вызовов Whisper или LLM в приёме нет.
[Главное правило](processing-ownership.md), [план перехода](refactoring-plan.md).

## Маршрут и доступ

`POST /internal/v1/transcription-results` использует
`Authorization: Bearer <SPEECH_WORKER_API_TOKEN>`. Ключ совпадает с ключом
исполнителя. Маршрут скрыт из пользовательского OpenAPI и не зависит от
браузерного режима `open`.

Пустая настройка ключа возвращает 503, отсутствующий или неправильный ключ —
401. Авторизация выполняется до сборки доступа к базе. Неправильный DTO
возвращает 422 с `{"detail":"invalid transcription result"}` без значений
полей и исходного текста. Пользовательский контракт `speech.api` остаётся 3.0.

## Вход

[TranscriptionDeliveryRequest](../src/application/dto/transcription_delivery.py)
содержит версию, идентификаторы захвата, снимок аудио и результат:

```json
{
  "contract_version": "1.0",
  "claim": {
    "call_id": "11111111-1111-4111-8111-111111111111",
    "job_id": "22222222-2222-4222-8222-222222222222",
    "claim_token": "33333333-3333-4333-8333-333333333333",
    "worker_id": "gpu-worker",
    "attempt": 1
  },
  "source": {
    "object_key": "calls/11111111-1111-4111-8111-111111111111.wav",
    "channels": 1
  },
  "result": {
    "engine": "whisper",
    "model_name": "large-v3",
    "model_digest": null,
    "language": "ru",
    "role_method": "none",
    "duration_s": 2.0,
    "replies": [
      {"seq": 0, "speaker": "unknown", "start_ms": 0, "end_ms": 1200, "text": "Здравствуйте."}
    ]
  }
}
```

UUID в примере условные. `claim_token` не выбирается отправителем: это nonce,
который очередь записала при конкретном захвате. `source.object_key` и
`source.channels` должны совпадать с сохранённым входом звонка. Для неизвестного
числа каналов передаётся null. Аудио, ключи моделей и итог анализа не передаются.
Полного текста отдельным полем нет: он собирается из реплик, как раньше.

Поля DTO запрещают переназначение; лишние поля запрещены. Результат исключён
из `repr` запроса. Проверяются длины метаданных, конечная неотрицательная
длительность, уникальные возрастающие `seq` и неотрицательные интервалы.
Ограничения: до 50 000 реплик и суммарно до 5 000 000 символов их текста.
Роли по тексту (`llm_attribution`) не принимаются. При `role_method=none`
все участники должны быть `unknown`; правила метода принадлежат domain.

## Выход и смысл подтверждения

При успехе возвращается 200 и `TranscriptionReceipt`:

- `contract_version`, `call_id`, `job_id`, `claim_token`, `attempt`;
- `transcript_id` — идентификатор сохранённого текста;
- `analysis_job_id` — поставленное или сброшенное задание анализа;
- `accepted_at` — время приёма по часам базы.

Ответ выходит только после успешного commit. Он означает, что расшифровка
сохранена и дальнейшая работа поставлена в очередь. Завершения анализа или
оценки маршрут не ждёт и готовые LLM-запросы воркеру не выдаёт.

Если звонка/задания нет или задание принадлежит другому звонку, возвращается
404. Чужой, просроченный или заменённый захват, изменённое аудио, несовпадающий
повтор и занятый конвейер дают 409 с нормализованной причиной.

## Захват и квитанция в существующей очереди

Новая таблица и миграция не нужны: используется `speech_jobs.payload`.
Ключи политики очереди, включая `not_before`, сохраняются.

- `_claim_token` — новый UUID при каждом `PostgresJobQueue.claim()` бэкенда.
  Доступен через `ClaimedJob.claim_token`. Heartbeat его не меняет.
- При fail/defer/возврате просроченной аренды и сбросе задания старые метаданные
  захвата/квитанции удаляются. Новый захват получает другой nonce, даже если
  `attempts` снова имеет то же значение и работает тот же `worker_id`.
- `_transcription_receipt` — SHA-256 канонического входного DTO и квитанция.
  Полного текста, аудио и секретов здесь нет.
- `_transcription_delivery` — временный полный DTO неподтверждённого ASR,
  сохранённый воркером до HTTP. Commit приёма удаляет его в той же транзакции,
  в которой записывает расшифровку и квитанцию. При defer/аварии буфер
  сохраняется; переобработка/терминальный отказ его удаляют. Сборщик API
  не хоронит готовый буфер на последней попытке.

Ключ повтора — пара `job_id`/`claim_token`. Одинаковый подтверждённый запрос
возвращает исходную квитанцию, не заменяя текст, время, роли и задания.
Другой результат под тем же ключом отклоняется. При переобработке, новом
захвате или удалении задания прежняя квитанция больше не подтверждает доставку.
Срок её жизни соответствует текущему поколению и сроку хранения задания.

Порядок ключей и пробелы JSON не меняют канонический хеш. Для сетевого повтора
отправитель должен сохранять исходный DTO; заново вычисленный отличающийся
результат не является тем же повтором.

## Транзакция и актуальность

Сценарий application через порт открывает короткую транзакцию:

1. Блокирует звонок, затем его задания через `FOR UPDATE NOWAIT`.
   Ожидание блокировки звонка ограничено тремя секундами.
2. Проверяет точный повтор или действующее задание `transcribe`: `running`,
   совпадающие владелец, попытка и nonce, непросроченная аренда.
   Для времени используется `clock_timestamp()` после получения блокировок.
3. Проверяет сохранённое аудио и состояние звонка. Работающий соседний этап
   или ожидающий повтор приёма блокирует замену входа.
4. Снимает прежние анализ/оценку, заменяет расшифровку и её реплики.
   Проектные сегмент/продукт сохраняются; результаты прежнего анализа сбрасываются.
5. Ставит свежий анализ с полосой/приоритетом расшифровки и лимитом попыток
   из настроек бэкенда. Терминальное или ожидающее прежнее задание анализа
   сбрасывается; неработающие задания старой оценки убираются.
6. Повторно проверяет живую аренду непосредственно при завершении задания
   и записи квитанции. Потеря аренды откатывает все предварительные изменения.
7. Делает commit и возвращает подтверждение. Потерянный после commit
   HTTP-ответ допускает точный повтор.

После записи звонок имеет `processing_status=analyzing`,
`analysis_status=pending`, `completed_at=null`. Новый текст уже доступен поиску.
Бэкенд определяет следующий этап; воркер не задаёт приоритет или вид дальнейшей
работы в DTO доставки. Сеть и модели внутри транзакции не вызываются.

## Проверки и состояние подключения

[Контракт/HTTP](../tests/test_transcription_delivery.py) проверяют DTO,
служебную авторизацию, безопасные ошибки и невозможность подтверждения
при отказе commit. [PostgreSQL](../tests/test_transcription_delivery_db.py)
проверяет повтор, смену nonce при defer/reprocess, устаревший вход, снятие
прежних результатов, конкурирующие дубли и rollback при потере аренды.

Схема остаётся `sp_0016_evaluation_jobs`. Рабочие `.env`, настройки Whisper,
фронтенд и сервер не изменяются. Основной `speech-worker` теперь доставляет
ASR этому маршруту и не завершает задание независимо от API.
[Восстановление и срок хранения буфера](../../speech-worker/docs/transcription-delivery.md).
Сохранённые отдельные LLM-команды — переходный код. Фоновый `analyze` уже
реализован в `speech-analyze`: [CPU-анализ](analysis-processing.md).
Фоновая оценка, удаление дублей и переключение сервера остаются отдельными задачами.
