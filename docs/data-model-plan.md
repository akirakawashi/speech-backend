# План модели данных и классификации

Дата: 14.10.2026. Владелец согласовал направление переработки БД после
разбора текущей схемы. Это архитектурное решение и план; новые таблицы,
миграции и служебные контракты вводятся отдельными шагами.
14.10.2026 добавочное хранение анализа реализовано в `sp_0017_analysis_storage`.
Действующие писатели/читатели ещё прежние; рабочие БД и сервер не переключены.

Первый шаг проектирования выполнен 14.10.2026:
[схема актуального анализа, потребители и порядок миграции](analysis-storage.md).
Уточнение владельца 14.10.2026: сравнение не требуется. Схема сохраняет один
текущий результат на звонок; архив прошлых успешных результатов для сравнения
не добавляем. История запусков — отдельная задача общего плана.
Таблицы, ORM, DTO и новая ревизия подготовлены; перенос данных/писателей
и история запусков ещё не реализованы.

## Согласованные решения

1. Сохраняем PostgreSQL для данных и надёжной очереди, MinIO для аудио.
   Отдельная база для каждого проекта и замена брокера сейчас не требуются.
2. Владельцем бизнес-данных и миграций остаётся бэкенд. Целевая граница
   воркера — получение технического задания и передача фактов/DTO через
   служебный контракт без SQL к бизнес-таблицам бэкенда.
3. Выделяем результат LLM-анализа из `speech_calls` в самостоятельную сущность,
   связанную со входом, моделью и версиями промпта/правил.
4. Добавляем историю запусков и попыток. Повторная обработка должна оставлять
   сведения о предыдущем исполнении, а не только заменять состояние задания.
5. Разбираем назначения старого справочника `speech_topics`, дерева
   `speech_classifier_nodes` и полей классификации до их объединения/удаления.
   Новые темы должны добавляться как данные справочника.

Правило обработки сохраняется: воркер выполняет получение/ASR, бэкенд
сохраняет расшифровку, управляет продолжением, вызывает LLM и сохраняет
проверенные итоги. [Владельцы операций](processing-ownership.md).

## Что есть сейчас

Бэкенд и воркер используют общую PostgreSQL. Это действующая переходная
реализация, а не уже выполненная изоляция хранилища бэкенда.

| Данные | Текущее хранение и ограничение |
| --- | --- |
| Звонок | `speech_calls`: метаданные, состояние аудио/обработки и многие поля результата LLM находятся в одной строке |
| Расшифровка | `speech_transcripts` и `speech_transcript_segments`: одна текущая расшифровка звонка; при замене прежняя удаляется |
| Задание | `speech_jobs`: одна строка на звонок и вид задания; при переобработке строка сбрасывается, отдельной истории исполнений нет |
| Доставка ASR | Подготовленный DTO и квитанция в `speech_jobs.payload`; подтверждение API атомарно сохраняет текст, завершает задание и убирает буфер |
| Оценка продаж | `speech_call_evaluations`: результат связан со звонком и редакцией скрипта; этапы/возражения хранятся в JSONB |
| Классификаторы | Дерево `speech_classifier_nodes`, прежний справочник `speech_topics` и отдельные поля операторской/модельной классификации |
| Остальные справочники | Проекты, сотрудники и причины обращения; их правила принадлежат бэкенду |
| Аудио | Объекты MinIO; ключ и состояние находятся в PostgreSQL, временные файлы очищает исполнитель |

Воркер ещё захватывает/обновляет задания SQL, сохраняет буфер ASR в общей
очереди и применяет технический результат ingest в транзакции этой базы.
Целевое владение БД не даёт основания немедленно удалить эти операции.
Действующие гарантии: [приём метаданных](intake-ownership.md),
[доставка ASR](../../speech-worker/docs/transcription-delivery.md).

## Целевая модель

Ниже логические сущности, а не окончательные имена таблиц или готовая миграция.
Точные поля, ключи и порядок переноса проектируются отдельными задачами.

| Сущность | Ответственность и связи |
| --- | --- |
| Звонок | Идентичность, источник, метаданные и ссылки на актуальные результаты; компактная проекция состояния для API |
| Расшифровка и реплики | Текст/таймкоды и сведения ASR; результат анализа ссылается на конкретный вход |
| Задание очереди | Планирование, приоритет, отсрочка, аренда и повтор; одна текущая строка задания не заменяет историю запусков |
| Запуск и попытка | Этап, идентификатор входа/его отпечаток, исполнитель/модель, начало/конец, исход и нормализованная ошибка |
| Результат анализа | Расшифровка/отпечаток входа, запуск, модель, версии промпта и правил, снимок классификатора, проверенные результаты LLM |
| Результат оценки | Связь с фактическим входом, запуском, моделью и редакцией скрипта; действительность определяется входом, включая роли |
| Справочники | Классификация, причины, проекты и сотрудники с устойчивыми идентификаторами и управлением доступностью |
| Доставка результата | Надёжно сохранённый неподтверждённый DTO, идентификатор доставки и квитанция бэкенда |

История исполнения и хранение всех прошлых текстов/ответов — разные вопросы.
Нужна история запусков, но бессрочное хранение каждого исходного и модельного
документа не согласовано. Сроки хранения, объём сохраняемого входа и правила
удаления предстоит определить. Одного отпечатка недостаточно, чтобы заново
получить удалённый текст; это учитываем при выборе требуемой воспроизводимости.

Чтение API может использовать актуальную проекцию/ссылку в звонке. Выделение
анализа не требует одновременно переписывать каждый отчёт. Переключение
записи, перенос старых значений и перевод читателей выполняются поэтапно.
Смена входа по-прежнему инвалидирует зависимые результаты; поздняя попытка
не может заменить более свежий успешный результат.

JSONB оставляем там, где сохраняется и читается цельный проверенный документ,
например набор этапов одной оценки. Отдельные таблицы для каждого поля
добавляются при реальной необходимости запросов и ограничений.

## Граница хранения между бэкендом и воркером

Бэкенд выдаёт задания, проверяет наблюдения исполнителя и фиксирует
бизнес-результат вместе с переходом очереди. Воркер получает запись, работает
с MinIO/Whisper и сообщает технический исход. Его загрузка объекта в MinIO
по команде бэкенда не делает воркер владельцем политики хранения.

До удаления прямого доступа воркера к PostgreSQL нужны контракты получения
задания, продления аренды, повторов и подтверждения результата. Сохраняем:

- защиту от записи исполнителем с истёкшей арендой/старым nonce;
- приоритеты, отсрочки, ограничения попыток и восстановление после аварии;
- идемпотентность при потере ответа после commit;
- атомарность сохранения результата и постановки следующего этапа;
- надёжный буфер готового ASR при недоступности API и после перезапуска.

Где будет храниться буфер после отказа от общей БД, пока не решено.
Память процесса и временный каталог аудио не заменяют этот буфер.
Выбор постоянного хранилища, его подтверждений и восстановления — часть
отдельного проектирования контракта. Сначала проверяем замену, затем
убираем прежний путь и права доступа воркера.

## Как классификация работает сейчас

Темы основного классификатора не перечислены в Python enum. Они находятся
в `speech_classifier_nodes`: UUID узла, родитель, уровень, подпись, ключ,
источник, порядок и доступность. Бэкенд загружает дерево в снимок входа
анализа, строит из активных веток JSON для LLM и проверяет возвращённый путь
по тому же снимку. Неизвестная часть пути отбрасывается; выдуманное название
не становится новой темой автоматически.

Основные места реализации:
[правила дерева](../src/domain/calls/classifier.py),
[загрузка снимка](../src/infrastructure/persistence/stages/analyze.py),
[подготовка входа LLM](../src/application/analysis/execution.py),
[проверка ответа](../src/domain/calls/analysis.py).

### Добавление темы

Есть импорт путей из JSON: [CLI](../src/presentation/cli/seed_classifier.py)
и [сценарий](../src/application/catalogues/service.py).
Формат: `{"paths": [["уровень 1", "уровень 2", "уровень 3", "новая тема"]]}`.
Из каталога `speech-backend` команда сначала показывает изменения:

```bash
uv run --locked speech-seed-classifier --file /path/to/classifier.json
uv run --locked speech-seed-classifier --file /path/to/classifier.json --apply
```

Это инструкция для дальнейшего использования, сейчас импорт не запускался.
Внешний JSON позволяет добавить тему без изменения Python и пересборки
пакета. Встроенный [classifier.json](../src/infrastructure/data/classifier.json)
остаётся исходным справочником для загрузки, рабочее дерево читается из БД.

Импорт добавляет недостающие узлы и обновляет/включает перечисленные.
Отсутствующий в файле узел сам по себе не выключается. Поэтому повторная
загрузка старого файла не заменяет операцию управления доступностью.
При приёме операторской классификации также создаются недостающие узлы
источника NCC. Это существующая политика, её пересмотр — отдельное решение.

Административный API сейчас поддерживает чтение дерева и переключение
`is_active`, включая исключение всей выключенной ветки из входа LLM.
Создания, переименования и переноса узлов через этот API пока нет.
Выключение не переписывает уже классифицированные звонки.
Новая тема попадёт в последующие снимки анализа; исторические звонки
автоматически заново не классифицируются.

### Что всё ещё ограничено кодом

| Ограничение | Последствие |
| --- | --- |
| `Segment`: `individual`, `b2b`; `Product`: `wallet`, `mobile`, `broadband` | Названия сегмента/продукта сопоставляются со значениями enum в `dimensions()`. Новый корень/продукт может появиться в дереве, но не получит новое значение соответствующего фильтра автоматически; нужны изменения кода и ограничений БД |
| Пять уровней, тема на уровне 4 | Ограничения есть в domain, БД и промпте. Новая соседняя тема/подтема допустима; шестой уровень требует изменения структуры |
| Семантика уровней в промпте | Сегмент, продукт, тип обращения, тема, уточнение закреплены инструкцией; часть примеров/типов обращения названа явно |
| Вход `classifier` ограничен 48 000 символов | Рендерер отклоняет превышение до вызова LLM. Рост дерева требует контроля размера, а не обещания неограниченного расширения |

Enum определены в [контрактах domain](../src/domain/calls/contracts.py),
ограничения БД — в [моделях](../src/infrastructure/persistence/models/speech.py),
размер и семантика входа — в [промпте](../src/infrastructure/data/prompts/analysis.json).
Проверка размера выполняется в [подготовке запроса](../src/application/model_requests/service.py).
Прежняя `speech_topics` не является рабочим деревом текущего LLM-анализа;
её поля/ссылки удаляем только после аудита оставшихся потребителей и данных.

### Требования к развитию справочника

- Новую тему в существующей структуре добавляем данными без релиза Python
  и без миграции для каждого названия.
- Идентичность темы отделяем от её подписи. Переименование/перемещение не
  должно незаметно переписывать смысл исторического результата; фиксируем
  редакцию или снимок справочника, использованный при анализе.
- Управление справочником принадлежит бэкенду; проверяем существование
  родителя, допустимую глубину, уникальность и отсутствие циклов.
- Выключение сохраняет историю; изменение тем не запускает массовую
  переобработку без отдельной команды.
- API создания/редактирования, аудит изменений и предварительная проверка
  размера промпта — запланированные возможности, а не уже готовая админка.

Если требуется так же свободно добавлять сегменты/продукты, нужно отдельно
спроектировать их справочники и сопоставления взамен текущих enum/словарей.
Этот вариант пока не реализован и не выбран как обязательная миграция.

## Порядок дальнейшей работы

1. Уточнить схему сущностей и потребителей: актуальный результат/история,
   связи входов, классификаторы, индексы, сроки хранения. Выбрать одну
   небольшую реализационную задачу с отдельной миграцией и проверками.
2. Поэтапно выделить анализ и историю запусков, перенести существующие
   данные и перевести писателей/читателей без удаления действующего пути
   до проверки его замены.
3. Добавить управление темами и сохранение использованной редакции/снимка
   классификатора. Отдельно решить судьбу прежних полей и справочников.
4. Заменить оставшийся прямой SQL воркера служебным контрактом вместе с
   надёжным хранением доставки; после проверок убрать старый доступ.
5. Завершить перенос синхронизации справочников и политик хранения в бэкенд,
   прогнать весь путь и подготовить переключение по
   [общему плану](refactoring-plan.md).

Порядок зависимых миграций, выбор хранилища буфера и сроки хранения уточняем
до реализации соответствующего шага. Создание этого документа не означает
выполнение перечисленных изменений схемы или развёртывания.
