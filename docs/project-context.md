# Контекст проекта и перенос кода

Состояние зафиксировано 12.10.2026. При изменении перечисленных решений
обновляем этот документ и ссылки в `AGENTS.md`.

## Отдельный бэкенд

12.10.2026 текущая реализация из `whisper-backend` скопирована в `speech-backend`.
Исходная папка сохранена без изменений. Решением владельца 11.10.2026 целевые
проекты разделены на `speech-backend`, `speech-worker` и `speech-frontend`.
Воркер пока входит в скопированный код; выделяем его следующим отдельным этапом.
Границы описаны в [архитектуре новых проектов](service-boundaries.md).

Код происходит из монорепозитория, но с 09.10.2026 развивается отдельно.
Описание источника остаётся в
[README, «Откуда код»](../README.md#откуда-код).

`aisistent-backend` не читаем, не меняем и не используем как источник повторного
копирования. Соседние фронтенд, инфраструктура и Dify не входят в задачу переноса
бэкенда. Git-репозиторий этой папки уже создан владельцем и сохранён при
копировании. Создание коммитов и смена процесса поставки не входят в копирование.

## Обезличивание и оценка

В этом бэкенде обезличивание расшифровки удалено. Сохраняем это поведение:

- после расшифровки следующий этап — разбор; этапа `mask` и статуса `masking` нет;
- текст хранится в `text_raw`; колонок `text_masked`, `pii_spans`, `masked_at` нет;
- ручки `/calls/{id}/reveal`, права `reveal_pii` и события `pii.reveal` нет;
- клиент guardrails и его настройки не возвращаем при переносе;
- оценка считается действующей относительно времени расшифровки `created_at`,
  а не времени обезличивания;
- текущая версия внешнего контракта `speech.api` — 3.0.

Изменение ролей реплик должно снимать оценку звонка. Не меняем правила
действительности оценки и пересчёта вместе с перемещением кода.

Номер клиента — отдельный вопрос: он остаётся маской и хешем, исходный номер
не хранился. Удаление обезличивания текста само по себе не восстанавливает
номера и не меняет хранение этого поля.

Оценка по скрипту продаж предназначена для звонков Телфина. NCC в эту оценку
не входит. При переносе это остаётся бизнес-правилом, а не настройкой SQL-запроса
или особенностью одного роутера.

## Окружение и базы

У папки своё окружение `.venv`; команды установки и проверки находятся в
[документе разработки](development.md#окружение).

| Назначение | База |
|---|---|
| Локальный speech-backend | `speech_whisper` |
| Тесты speech-backend | `speech_whisper_test` |

Базы находятся в локальном контейнере `speech-postgres`. Базы монорепозитория
`speech` и `speech_test` не подставляем вместо них: схема и поведение различаются.
При подготовке тестовой базы используем миграции из этой папки.

Сквозная локальная проверка выполняется через `local-dev` из рабочего каталога
Whisper. Его `run.sh` по умолчанию выбирает `whisper-backend`; новую папку
выбираем через `SPEECH_BACKEND=speech-backend`. Для слоистых бэкендов скрипт
запускает `src` напрямую. API из `speech-backend` также запускается командами из
[README](../README.md#запуск). Сервер icai из WSL недоступен; локальная модель
меньше боевой, поэтому локальный запуск подходит
для проверки связности и экрана, но не для вывода о качестве модели.

## Переход со старой структуры

Рабочие пакеты описаны в [архитектуре](architecture.md). Реализация перенесена
в `src/`; дубли старого кода из `app/` удалены. Переходные точки запуска
также удалены из `speech-backend` после перевода внешнего `local-dev/run.sh`
на CLI и HTTP-фабрику из `src/`. При переименовании миграций в `alembic/` его
команда `migrate` переведена на `alembic.ini`; для монорепозитория остаётся
поддержка прежнего имени конфига.

Переносим один законченный сценарий за раз:

1. Определяем вход, выход, побочные эффекты, внешние контракты и существующие
   проверки сценария.
2. Отделяем бизнес-правила в `domain`, контракты и последовательность действий —
   в `application`.
3. Выделяем реализации портов в `infrastructure` и подключаем их через `di`.
4. Переводим нужные точки входа в `presentation`, сохраняя их внешнее поведение.
5. Запускаем проверки и обновляем документацию о перенесённом сценарии.

Старые точки входа при необходимости остаются тонкими переходными обёртками,
которые вызывают новую реализацию. Новые `presentation`, `application` и `domain`
не импортируют старую реализацию. Не держим две версии одного бизнес-правила;
переходные обёртки удаляем после перевода их потребителей в рамках
соответствующей задачи.

Если старую интеграцию нужно временно использовать, изолируем её за портом и
адаптером `infrastructure` и документируем временную зависимость. Не объявляем
весь старый модуль инфраструктурой, если в нём смешаны сценарий, транспорт и
бизнес-правила.
