# Единый запуск воркера

Решение владельца 12.10.2026: одна команда `speech-worker` запускает постоянный
обработчик очереди и приём записей по расписанию. Оценка продаж включена
в общую очередь. Отдельные контейнеры и таймеры приёма не нужны.

## Ответственность

Бэкенд задаёт расписание, дневную долю NCC, приоритеты источников и выбирает
звонки для оценки. Он хранит скрипт продаж, готовит промпты, выбирает модель,
проверяет ответы и считает результат. Воркер получает готовые команды,
перечисляет записи, скачивает аудио и вызывает существующие HTTP-сервисы.

Воркеры и API используют общую PostgreSQL. Миграциями владеет бэкенд;
новая требуемая ревизия — `sp_0016_evaluation_jobs`. Миграция расширяет
ограничение вида задания и добавляет лимит попыток оценки, не переписывая
существующие настройки. Рабочая база автоматически не мигрируется.

## Расписание

| Действие | По умолчанию | Настройка бэкенда |
| --- | --- | --- |
| Приём NCC | Каждые 15 минут | `SPEECH_NCC_INGEST_INTERVAL_SECONDS=900` |
| Приём Телфина | Раз в час, только ночью | `SPEECH_TELPHIN_INGEST_INTERVAL_SECONDS=3600` |
| Постановка оценки | Каждые 15 минут, до 100 звонков | `SPEECH_QUALITY_INTERVAL_SECONDS=900`, `SPEECH_QUALITY_BATCH_LIMIT=100` |

`SPEECH_DISPLAY_TIMEZONE` — часовой пояс расписания, по умолчанию Москва.
Ночь задаётся `SPEECH_NIGHT_FROM=19` и `SPEECH_NIGHT_UNTIL=7`, конец исключается.
`SPEECH_NCC_IMMEDIATE_SHARE=0.5` сохраняет дневную долю NCC. Ночью NCC
обрабатывается сразу; днём отложенная половина ждёт начала ночи.

Приоритеты приёма сохранены: свежие NCC — 0, отложенные — 10, Телфин — 20,
история — 100. Оценка получает приоритет не выше срочности источника:
обычные задания — 30, оценки истории — 100. Оценка остаётся круглосуточной.

На старте доступное действие выполняется сразу. Днём Телфин ждёт ночи.
Затем сроки привязываются к границам интервалов. После простоя выполняется
один догон; отдельного запуска на каждый пропущенный интервал нет.
Приём перечитывает вчера и сегодня и сохраняет прежний механизм истории
Телфина. Для более старой истории NCC остаётся `speech-backfill`.

## Служебный контракт 1.0

Все маршруты скрыты из браузерного OpenAPI и используют
`Authorization: Bearer <SPEECH_WORKER_API_TOKEN>`. Пустой настроенный ключ
даёт 503, неверный — 401. Некорректный вход даёт 422 без его значений.

- `POST /internal/v1/worker-plan`: `MaintenanceRequest` с действием и моментом
  его последнего запуска → `MaintenancePlan` со сроком, относительным ожиданием
  и готовой командой. Разница часов машин не используется для расчёта ожидания.
- `POST /internal/v1/quality-jobs`: `QualityQueueRequest` с охватом →
  `QualityQueueReport`. С `apply=false` проверяет кандидатов; с `apply=true`
  ставит задания. `drop_stale` сохраняет прежнюю ручную сверку оценок.
- `POST /internal/v1/quality-steps`: `QualityStepRequest` с UUID звонка,
  исходным снимком и уже полученными ответами → `QualityStep` с очередным
  запросом модели либо проверенным `QualityWork`.

Подготовка оценки использует существующий сценарий определения ролей,
оценки и проверки. Бэкенд воспроизводит его по уже полученным ответам,
останавливаясь на следующем невыполненном запросе. Повторных вызовов LLM
при воспроизведении нет. Это позволяет сохранить правила и проверки в одном
месте; контекст передаётся в DTO и не хранится в памяти процесса API.
На один разговор допускается не больше 1024 вызовов модели.
При повторе задания после сбоя выполнение начинается заново.

## Очередь и запись результатов

`evaluate` — независимый вид задания, а не обязательное продолжение `analyze`.
Бэкенд выбирает только готовые звонки Телфина с расшифровкой. NCC не оценивается.
Активные задания исключаются до `LIMIT`, поэтому следующая порция не застревает
на первых уже поставленных звонках. Терминальное задание можно сбросить при
изменении входа или ручном повторе. Действующая оценка и уже записанный отказ
исключаются плановым `skip_failed`.

Вызовы модели выполняются без открытой транзакции. При записи блокируются
и сверяются исходные реплики и время расшифровки. Роли, готовый балл и счётчики бэкенда
сохраняются вместе с завершением принадлежащей воркеру аренды. Потеря аренды
откатывает запись; изменённый текст отправляет задание на повтор.
Сетевые ошибки используют повторы очереди. На последней попытке модельного
вызова сохраняется нормализованный отказ; ошибки инфраструктуры могут
завершить задание как `dead`. Плановый запуск не оживляет его бесконечно.

Оценка сохраняет `processing_status` и `completed_at` звонка. Окончательный
отказ оценки не делает успешную расшифровку неудавшейся. Повтор только оценки
через административную команду тоже сохраняет текст и результат анализа.

## Переключение

Остановить старые воркеры и таймеры для этой базы, применить миграцию,
обновить API и запустить новый воркер. Один процесс выполняет одно задание
за раз. Прогоны приёма выполняются независимо и не вызывают GPU-модели.
Несколько экземпляров сохраняют защиту PostgreSQL от дублей, но увеличивают
число одновременных модельных заданий; сейчас запускаем один экземпляр.

Исходные проекты, действующие сервисы и рабочие `.env` автоматически
не изменяются. Порядок запуска: [бэкенд](deployment.md),
[воркер](../../speech-worker/docs/deployment.md).
