# План завершения разделения бэкенда и воркера

Дата плана: 12.10.2026. Обновлён: 13.10.2026. Статус: выполнение по частям.
Документ фиксирует порядок следующих этапов и результаты выполненных шагов.
Изменение этого документа не запускает миграции, не удаляет старую реализацию
и не переключает действующие сервисы.

## Цель

Бэкенд принимает бизнес-решения: какие звонки обрабатывать, когда, какие этапы
выполнять, нужен ли вызов LLM и как трактовать его ответ. Воркер получает
конкретное задание, выполняет технические операции и сохраняет проверенный
результат. У каждого правила должен быть один владелец.

Оба проекта сохраняют шесть слоёв: `presentation`, `application`, `domain`,
`infrastructure`, `setting`, `di`. Между слоями и сервисами передаются Pydantic
DTO. Сценарии обращаются к внешним операциям через порты; SQL и HTTP остаются
в infrastructure, сборка зависимостей — в DI.

## Что уже есть

- Самостоятельные `speech-backend` и `speech-worker`, окружения UV,
  `pyproject.toml`, `uv.lock`, Docker-образы и собственные проверки.
- API, авторизация, права, поиск, отчёты и администрирование в бэкенде.
- Промпты анализа и выбор моделей в бэкенде; прямые HTTP-вызовы LLM в воркере.
  Dify в новых проектах не используется.
- Один постоянный процесс `speech-worker`: приём по расписанию и
  последовательное выполнение `ingest`, `transcribe`, `analyze`, `evaluate`.
- План расписания от бэкенда: NCC каждые 15 минут, Телфин каждый час ночью,
  постановка оценки каждые 15 минут. Приём не блокирует обработку очереди.
- Оценка продаж: бэкенд выбирает звонки Телфина, подготавливает шаги, проверяет
  ответы и рассчитывает балл. Воркер выполняет запросы и сохраняет готовый итог.
- Общая PostgreSQL с очередью `speech_jobs`; миграции принадлежат бэкенду.
  Текущая требуемая ревизия — `sp_0016_evaluation_jobs`.
- Защита аренды задания, технические повторы, атомарная запись результатов
  и очистка собственных временных файлов воркера.

Оценка уже использует требуемое разделение. Анализ пока разделён частично:
бэкенд готовит запрос, а воркер ещё проверяет и интерпретирует ответ.
Прежние фоновые команды и их зависимости сохранены в бэкенде.
Сервер пока не переключён на новые проекты.

Подробности текущего состояния: [границы сервисов](service-boundaries.md),
[запросы к LLM](model-execution.md), [единый процесс](worker-runtime.md).

## Границы ответственности после переноса

| Операция | Владелец |
| --- | --- |
| Допуск звонка к обработке, короткие записи, следующие этапы | Бэкенд |
| Дневная доля NCC, ночная отсрочка, приоритет, правила истории | Бэкенд |
| Промпт, модель, необходимость вызова, проверка и трактовка ответа | Бэкенд |
| Классификация, причина обращения, тональность, роли по тексту, резюме | Бэкенд |
| Скрипт продаж, охват оценки, балл и пригодность оценки | Бэкенд |
| Запрос списка записей и скачивание из источника | Воркер |
| MinIO, ffmpeg/ffprobe, подготовка WAV, измерение аудиоканалов | Воркер |
| HTTP-вызовы Whisper и LLM по готовой команде | Воркер |
| Захват задания, heartbeat, технический backoff, остановка, очистка файлов | Воркер |
| Запись результата и следующего задания в одной транзакции | Воркер, по решению бэкенда |
| Миграции, пользовательский API и права доступа | Бэкенд |

Измерение энергии каналов остаётся технической операцией воркера. Правило,
когда использовать результат измерения и можно ли заменить известные роли
ответом модели, принадлежит бэкенду.

Общую PostgreSQL и существующий механизм очереди сохраняем. Замена брокера,
разделение базы и новый общий Python-пакет не входят в этот план.

### Ограничения контрактов и транзакций для этапов 1–2

- DTO содержит идентификаторы задания/звонка, контекст попытки и сведения
  для проверки актуальности входа. ORM, HTTP-объекты и секреты в DTO не входят.
- Бэкенд проверяет допустимость действия по текущему состоянию данных;
  произвольные поля DTO не позволяют обойти ограничения источника или этапа.
- Служебный доступ использует существующий Bearer-токен. Неизвестные версии,
  лишние поля и противоречивые исходы отклоняются до вызова модели или записи.
  Пользовательский HTTP-контракт `speech.api` 3.0 сохраняется.
- Новые DTO версионируются отдельно от пользовательского API. Проверяются
  совместимость двух проектов, размеры входа/ответов и отсутствие текста
  разговоров и секретов в сообщениях ошибок и обычных логах.
- Вызовы источников, бэкенда и моделей выполняются вне транзакции записи
  воркера. Служебная подготовка не завершает задание очереди.
- Проверенный результат, статусы, завершение принадлежащей воркеру аренды
  и следующее задание записываются вместе. Потеря аренды откатывает изменения.
- Перед записью проверяется актуальность входа: повторная расшифровка,
  правка ролей/справочников или перепостановка не должны принять устаревший
  результат. Состав снимка определяется для каждого сценария.
- Недоступность бэкенда приводит к техническому повтору. Не вводить
  запасное выполнение старых бизнес-правил внутри воркера.

- [ ] Зафиксировать совместимую пару версий API/воркера и ожидаемую ревизию
  схемы. Для текущего состояния нужна `sp_0016_evaluation_jobs`; дополнительные
  миграции добавлять только при фактической необходимости новых изменений.
- [ ] Проверить резервную копию базы и записать порядок восстановления.
  Откат приложения должен учитывать совместимость схемы и заданий; не
  обещать безопасный downgrade с удалением новых заданий в рабочей базе.
- [ ] Остановить старые обработчики и таймеры, обслуживающие ту же базу,
  дождаться активных заданий, применить миграции, запустить API и проверить
  `/ready`, затем запустить один новый воркер.
- [ ] Проверить прохождение свежих звонков, оценки Телфина, приоритеты,
  логи/метрики, перезапуск и очистку временного диска после переключения.

Этот этап относится к развёртыванию. Планирование и локальный рефакторинг
не означают, что удалённый сервер, Kubernetes или действующие таймеры изменены.
Инструкции: [API](deployment.md), [воркер](../../speech-worker/docs/deployment.md).

## Что не входит в этот этап

- Работа с фронтендом, исходными `aisistent-backend` и `whisper-backend`.
- Возвращение обезличивания или изменение договорённости об оригиналах MinIO.
- Подключение GigaAM, PyTorch/CUDA и локального инференса.
- Батчи аудио, несколько параллельных обработчиков и настройка моделей
  ради повышения производительности.
- Изменение внешнего Dify и посторонней инфраструктуры.

## Когда разделение считается завершённым

- [ ] Анализ, оценка и решения о ходе обработки имеют одного владельца — бэкенд.
- [ ] Воркер выполняет готовые DTO и технические операции без старых правил.
- [ ] Сохранены приоритеты, отсрочка, статусы и атомарность очереди.
- [ ] Удалены проверенные дубли, лишние точки запуска, настройки и зависимости.
- [ ] Оба проекта собираются и запускаются независимо; проверки пройдены.
- [ ] Сквозной прогон на стенде подтверждён; документация отражает фактический код.

Готовность к развёртыванию и выполненное переключение отмечаются отдельно.
После каждого этапа записывать здесь результат, выполненные проверки,
оставшиеся ограничения и ссылки на соответствующие изменения.
