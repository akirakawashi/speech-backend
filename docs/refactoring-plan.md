# План завершения разделения бэкенда и воркера

Дата плана: 12.10.2026. Цель уточнена владельцем 13.10.2026.
Статус: выполнение по частям. Изменение плана не запускает миграции,
не удаляет текущие обработчики и не переключает действующие сервисы.

## Главное правило

Воркер получает запись, готовит аудио, вызывает распознавание и передаёт
результат бэкенду. Бэкенд принимает и сохраняет расшифровку, определяет
дальнейшие этапы, сам вызывает LLM, проверяет ответы и сохраняет итоги
анализа и оценки.

Правило заменяет прежний вариант, в котором воркер исполнял готовые
LLM-запросы. Новый HTTP-маршрут передачи LLM-ответа от воркера сервису разбора
больше не планируем. Приём и доставка распознавания реализованы;
следующая задача — CPU-обработчик анализа и оценки в бэкенде.
Владельцы операций и гарантии: [главное правило](processing-ownership.md).

## Фактическое состояние

- Проекты самостоятельные, со слоями `presentation`, `application`, `domain`,
  `infrastructure`, `setting`, `di`, Pydantic DTO/Settings и окружениями UV.
- Промпты и выбор LLM находятся в бэкенде. Отдельные команды LLM в
  `speech-worker` ещё сохранены до переноса их потребителей.
- Основной процесс воркера принимает записи по расписанию, исполняет только
  `ingest`/`transcribe` и доставляет DTO бэкенду. Клиенты LLM он не создаёт.
- Правила и разбор оценки уже находятся в бэкенде, но сами вызовы модели
  и запись итогов оценки тоже предстоит передать исполнителю бэкенда.
- Уже выделен самостоятельный сервис разбора анализа в бэкенде.
- Миграциями владеет бэкенд, текущая ревизия — `sp_0016_evaluation_jobs`.
  Сервер на новые проекты не переключён.
- Реализованы служебный приём распознавания и доставка из воркера. Буфер
  неподтверждённого DTO и квитанция находятся в метаданных задания.

## Порядок реализации

Работа идёт отдельными проверяемыми задачами. Сначала фиксируем контракт
приёма распознавания в бэкенде, затем подключаем доставку из воркера и
фоновую обработку в бэкенде. После замены потребителей удаляем дубли.
Частичные изменения не переключают действующие сервисы.

- [x] В application проверить допустимость и актуальность результата через

  результат должен соответствовать действующему заданию и попытке.
- [x] Сохранить расшифровку, состояние задания распознавания и постановку

  зависимого анализа/оценки при замене входа.
- [x] Обеспечить идемпотентный повтор после потерянного HTTP-ответа:
  тот же результат возвращает прежнее подтверждение, а другой или устаревший
  результат не перезаписывает актуальный вход.
- [x] Проверить неподтверждённый результат, отказ до commit, потерю ответа
  после commit, потерю аренды и перепостановку звонка.

Критерий завершения: бэкенд надёжно принимает и сохраняет результат через
служебный контракт; подтверждение означает commit и постановку дальнейшей
работы, а не завершение анализа. Пользовательский API остаётся версии 3.0.

Реализация: `POST /internal/v1/transcription-results`, DTO контракта 1.0,
новый nonce при каждом захвате и квитанция/хеш в `speech_jobs.payload`.
Миграция не требуется; схема 16 сохраняется. Повтор в том же поколении
возвращает прежнюю квитанцию; переобработка/новый захват отклоняют старую доставку.
Приём не вызывает LLM. Описание и ограничения:
[контракт доставки](transcription-delivery.md).

Критерий завершения: путь «запись → Whisper → DTO → подтверждение бэкенда»
проверен; воркер не выполняет LLM-вызов после распознавания. До готовности
фонового обработчика бэкенда частичный перенос на сервере не включается.

Реализация: независимые DTO 1.0, порт буфера и HTTP-клиент, nonce каждого
захвата и fencing для heartbeat/defer/fail. Перед HTTP полный DTO сохраняется
в `_transcription_delivery`; commit бэкенда атомарно заменяет его квитанцией.
Отсрочка/авария после подготовки сохраняет ASR даже на последней попытке;
новый захват переиспользует результат только для прежнего входа. Новые миграции,
зависимости и настройки не добавлялись. Старые LLM-команды сохраняются до этапа 4,
но реестр/CLI основного процесса их больше не принимают.
[Подробности и срок хранения](../../speech-worker/docs/transcription-delivery.md).

## Критерии завершения

- [ ] Воркер получает/готовит запись, распознаёт и доставляет результат бэкенду.
- [ ] Бэкенд подтверждает сохранение расшифровки и надёжно планирует дальнейшую работу.
- [ ] Вызовы LLM, анализ, оценка и сохранение итогов принадлежат только бэкенду.
- [ ] Сохранены идемпотентность, приоритеты, статусы, актуальность и атомарность.
- [ ] Проверенные дубли, лишние настройки, маршруты и зависимости удалены.
- [ ] Проверки и сквозной прогон выполнены; документация описывает фактический код.

После каждой отдельной задачи записывать результат и проверки в этом плане.
Не отмечать перенос завершённым лишь после изменения документации.
