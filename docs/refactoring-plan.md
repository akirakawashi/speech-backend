# План завершения разделения бэкенда и воркера

Дата плана: 12.10.2026. Цель уточнена владельцем 13.10.2026.
Статус: выполнение по частям. Изменение плана не запускает миграции,
не удаляет текущие обработчики и не переключает действующие сервисы.

## Главное правило

Воркер получает запись, готовит аудио, вызывает распознавание и передаёт
результат бэкенду. Бэкенд принимает и сохраняет расшифровку, определяет
дальнейшие этапы, сам вызывает LLM, проверяет ответы и сохраняет итоги
анализа и оценки.

Правило заменяет прежний вариант, в котором воркер исполнял готовые
LLM-запросы. Новый HTTP-маршрут передачи LLM-ответа от воркера сервису разбора
больше не планируем. Приём и доставка распознавания реализованы;
CPU-анализ и оценка реализованы; вспомогательные команды работают в бэкенде,
LLM-код воркера и его служебные маршруты удалены. Далее — остальные политики
справочников/хранения и переключение; дубли получения/ASR удалены 14.10.2026.
Владельцы операций и гарантии: [главное правило](processing-ownership.md).

14.10.2026 владелец согласовал направление переработки БД: PostgreSQL/MinIO
сохраняются; бизнес-данными владеет бэкенд; анализ выделяется из звонка,
появляется история запусков, назначения классификаторов проверяются до удаления.
Решения, текущие ограничения добавления тем и открытые вопросы:
[план модели данных](data-model-plan.md). Добавочная схема `sp_0017` реализована;
перенос записи/чтения анализа и отказ от прямого SQL воркера ещё не выполнены.

## Фактическое состояние

- Проекты самостоятельные, со слоями `presentation`, `application`, `domain`,
  `infrastructure`, `setting`, `di`, Pydantic DTO/Settings и окружениями UV.
- Промпты, выбор LLM и модельные команды находятся только в бэкенде.
  Из `speech-worker` удалены клиенты и бизнес-код анализа/оценки.
- Основной процесс воркера исполняет только
  `ingest`/`transcribe` и доставляет DTO бэкенду. Клиенты LLM он не создаёт.
- `speech-process` выполняет анализ и оценку отдельным CPU-процессом бэкенда:
  локальные промпты, прямой LLM, снимок входа и атомарный исход задания.
  Постановка оценки по расписанию независима от долгого вызова модели.
- Уже выделен самостоятельный сервис разбора анализа в бэкенде.
- `speech-analyze` выполняет анализ отдельным CPU-процессом бэкенда:
  локальный промпт, прямой LLM, снимок входа, fencing и атомарный исход задания.
- Миграциями владеет бэкенд, текущая ревизия кода — `sp_0017_analysis_storage`.
  Сервер на новые проекты не переключён.
- Реализованы служебный приём распознавания и доставка из воркера. Буфер
  неподтверждённого DTO и квитанция находятся в метаданных задания.

## Порядок реализации

Работа идёт отдельными проверяемыми задачами. Сначала фиксируем контракт
приёма распознавания в бэкенде, затем подключаем доставку из воркера и
фоновую обработку в бэкенде. После замены потребителей удаляем дубли.
Частичные изменения не переключают действующие сервисы.

Критерий завершения: бэкенд надёжно принимает и сохраняет результат через

возвращает прежнюю квитанцию; переобработка/новый захват отклоняют старую доставку.
Приём не вызывает LLM. Описание и ограничения:
[контракт доставки](transcription-delivery.md).

- Полный анализ сохраняет `speech_call_analyses` и использованные справочники
  вместе с прежними полями, ролями, снятием оценок и done задания.
- Application формирует происхождение из фактов реального запроса, исходного
  снимка и захвата; отдельный хеш фиксирует состояние после собственных ролей.
  Проектные измерения сохраняют приоритет; предложение LLM хранится отдельно.
- Один звонок имеет один текущий результат. Полный повтор заменяет весь набор,
  ревизия увеличивается. Не добавлен архив успешных результатов.
- Причина получает REPEATABLE READ снимок и проверяет текст/роли/справочник,
  UUID/revision и отсутствие кода под блокировками после LLM. Отчёт учитывает
  только подтверждённые сохранения; изменения/конкуренция дают skipped.
- Причина сохраняет независимое происхождение полного анализа. Старые поля
  затронутого звонка при необходимости переносятся как legacy_observed без
  выдуманных сведений; массовый перенос ещё не выполнялся.
- Replay анализа/аудио и новый ASR снимают текущий результат атомарно.
  Повтор оценки и повтор подтверждённой квитанции ASR сохраняют свежий анализ.
- Миграции, зависимости, API, рабочие БД и `.env` сохранены. Воркер не менялся,
  сервер не переключён. [Код, гарантии и проверки](analysis-persistence.md).
