# Правила работы с speech-backend

## Область работы

- Сейчас работаем с `speech-backend` и `speech-worker`; `speech-frontend` оставляем
  для следующего этапа.
- Текущий код скопирован из `whisper-backend` 12.10.2026. Исходную папку
  сохраняем; код воркера пока входит в копию до отдельного этапа разделения.
- `aisistent-backend` не читаем, не меняем и не используем для копирования.
- Не меняем внешнюю инфраструктуру, Dify и его воркфлоу в рамках переноса.
- Git-репозиторий создан владельцем. При работе сохраняем его настройки.

## Архитектура и код

- Используем `src/presentation`, `src/application`, `src/infrastructure`,
  `src/domain`, `src/setting` и `src/di`.
- Presentation преобразует HTTP-ввод в DTO и вызывает application. Application
  применяет domain и обращается к внешним операциям через порты.
- Infrastructure реализует порты, DI собирает зависимости. Domain независим
  от остальных слоёв; application не импортирует infrastructure.
- Используем Python 3.12, Pydantic 2 для DTO и моделей, Pydantic Settings для
  настройки окружения. Настройки и клиенты создаём при сборке приложения.
- Пишем понятные русские докстринги: действие, вход, выход, значимые ошибки
  и побочные эффекты. Поддерживаем строгую типизацию.
- Контракты между проектами явные и версионируемые. Каждый проект собирается
  самостоятельно; runtime-импорты исходников соседнего проекта не используем.
- Не возвращаем обезличивание расшифровок. Оценка продаж применяется к Телфину.

## Проверки и документация

- После изменения Python-кода запускаем Ruff, проверку форматирования, mypy
  и подходящие pytest-тесты в окружении проекта.
- Не ослабляем проверки и не подавляем ошибки ради успешного прогона.
- Базы `speech` и `speech_test` монорепозитория не используем для тестов;
  существующая отдельная тестовая база — `speech_whisper_test`.
- Решения записываем в `docs/` и добавляем ссылки сюда. Для изменений только
  документации проверяем ссылки и согласованность.
