# Правила работы с speech-backend

## Область работы

- Сейчас работаем с `speech-backend` и `speech-worker`; `speech-frontend` оставляем
  для следующего этапа.
- Текущий код скопирован из `whisper-backend` 12.10.2026. Исходную папку
  сохраняем. 12.10.2026 воркер выделен в `speech-worker`; прежний код
  в бэкенде был оставлен до проверки потребителей; по решению владельца
  14.10.2026 старый аудиоворкер и его запуск удалены.
- `aisistent-backend` не читаем, не меняем и не используем для копирования.
- Не меняем внешнюю инфраструктуру, Dify и его воркфлоу в рамках переноса.
- Git-репозиторий создан владельцем. При работе сохраняем его настройки.

## Архитектура и код

- Используем `src/presentation`, `src/application`, `src/infrastructure`,
  `src/domain`, `src/setting` и `src/di`.
- Пакет `app` удалён. HTTP запускаем фабрикой `src.di.http:create_app --factory`,
  CLI — модулями `src.presentation.cli.*`. Старые обёртки не восстанавливаем.
- Главное правило владельца 13.10.2026: воркер получает запись, готовит аудио,
  распознаёт речь и доставляет DTO бэкенду. Бэкенд принимает и сохраняет
  расшифровку, управляет дальнейшими этапами, сам вызывает LLM, проверяет
  ответы и сохраняет результаты анализа/оценки.
- Долгие LLM-вызовы выполняет надёжный фоновый обработчик проекта бэкенда
  на CPU; API приёма подтверждает сохранение без ожидания анализа.
  `speech-process` последовательно исполняет `analyze`/`evaluate` и независимо
  ставит оценку по расписанию. Для обычного запуска используем один CPU-процесс;
  `speech-analyze` сохранён для отдельного режима только анализа.
  Запись итога и завершение задания атомарны; потеря nonce/аренды или смена
  снимка запрещают запись. Сборщик ограничен видом задания и полосами процесса.
  LLM-код и запись его итогов из воркера удалены 13.10.2026.
  Передачу готовых LLM-запросов воркеру не возвращаем.
- Бэкенд владеет промптами, выбором LLM, её HTTP-клиентами и секретами.
  Dify не используем. Промпты храним в `src/infrastructure/data/prompts/`,
  применяем через порт.
- Presentation преобразует HTTP-ввод в DTO и вызывает application. Application
  применяет domain и обращается к внешним операциям через порты.
- Infrastructure реализует порты, DI собирает зависимости. Domain независим
  от остальных слоёв; application не импортирует infrastructure.
- Используем Python 3.12, Pydantic 2 для DTO и моделей, Pydantic Settings для
  настройки окружения. Настройки и клиенты создаём при сборке приложения.
- В `.env.example` оставляем действующие параметры без исторических пояснений;
  рабочие `.env` сохраняем. Неиспользуемый код удаляем после проверки точек
  входа и зависимостей; отсутствие прямого вызова у ORM или роутера недостаточно.
- Пишем понятные русские докстринги: действие, вход, выход, значимые ошибки
  и побочные эффекты. Поддерживаем строгую типизацию.
- Контракты между проектами явные и версионируемые. Каждый проект собирается
  самостоятельно; runtime-импорты исходников соседнего проекта не используем.
- Не возвращаем обезличивание расшифровок. Оценка продаж применяется к Телфину.
- Решение владельца 14.10.2026: PostgreSQL/MinIO сохраняем; целевое хранение
  бизнес-данных принадлежит бэкенду, воркер работает через служебный контракт.
  Анализ выделяем из звонка, добавляем историю запусков; изменения схемы
  выполняем поэтапно. Текущую общую очередь и буфер ASR не удаляем до проверки
  их замены. Темы — данные справочника, новые названия не добавляем в enum.
  [Модель данных, ограничения классификации и открытые решения](docs/data-model-plan.md).
- Первая схема анализа и добавочная миграция реализованы 14.10.2026:
  [хранение анализа](docs/analysis-storage.md). Новая ревизия
  `sp_0017_analysis_storage` последовательно идёт после `sp_0016_evaluation_jobs`.
  ORM и DTO готовы; действующие писатели/читатели и поля звонка сохранены.
  На рабочих БД миграция не запускалась. Первая реализация сохраняет
  один актуальный результат на звонок. Уточнение владельца 14.10.2026:
  сравнение не требуется, архив успешных версий для сравнения не добавляем.
  Частичная причина имеет отдельное происхождение и не означает
  готовности полного анализа. Метаданные нового запроса берём у исполнителя,
  сведения о старом запросе не восстанавливаем из текущих Settings.

## Проверки и документация

- Окружением и зависимостями управляет UV: `pyproject.toml` и `uv.lock`.
  Установка — `uv sync --locked`, команды — `uv run --locked`.
  Сборщик — `uv_build`; dev-инструменты находятся в группе `dev`.
  requirements-файлы и setuptools не добавляем. Подробнее:
  [окружение](docs/development.md#окружение).
- После изменения Python-кода запускаем Ruff, проверку форматирования, mypy
  и подходящие pytest-тесты в окружении проекта.
- Не ослабляем проверки и не подавляем ошибки ради успешного прогона.
- Базы `speech` и `speech_test` монорепозитория не используем для тестов;
  существующая отдельная тестовая база — `speech_whisper_test`.
- Решения записываем в `docs/` и добавляем ссылки сюда. Для изменений только
  документации проверяем ссылки и согласованность.

14.10.2026 приём метаданных/истории и бизнес-решения ingest перенесены в бэкенд.
`speech-process` отдельно от LLM опрашивает источники и планирует задания.
`speech-ingest`/`speech-backfill` принадлежат бэкенду. Воркер не перечисляет
звонки, не выбирает короткую/отсутствующую запись и не назначает следующий этап:
он получает готовую команду через `ingest/prepare`, передаёт наблюдения через
`ingest/resolve` и применяет ответ одной транзакцией очереди. Финальный commit
проверяет живой nonce; решение попытки хранится без URL в `_ingest_admission`.
`worker-plan` и его потребитель удалены. Повторный приём не бросает жребий
дневной доли повторно; поздний прогон истории не отменяет паузу/новое окно.
Рабочие `.env` сохранять. Справочники и хранение остаются переходными.
[Владение приёмом, совместимость и остаток работ](docs/intake-ownership.md).

14.10.2026 из бэкенда удалены старые обработчики получения/ASR, общий worker CLI/DI,
ffmpeg, клиент Whisper и загрузка оригиналов в MinIO. Метаданные, приём ASR,
CPU-анализ/оценка, API чтения аудио, ORM и миграции сохранены. Поле
`SPEECH_WHISPER_BASE_URL` нужно только необязательной пробе `GET /models`
в админке; остальные ASR-настройки принадлежат воркеру. Старый путь запуска
не восстанавливать; в `local-dev` новый бэкенд использует отдельный воркер
и CPU-команду анализа. [Потребители, совместимость и остаток](docs/audio-worker-removal.md).
